# Orchestrating Parallel Workstreams

## Overview
One **orchestrator** drives many autonomous coding subagents — one per workstream, each in its own git worktree — from a master plan, pipelines their PRs through a multi-model adversarial review gate, and surfaces decisions. **The orchestrator dispatches, verifies, and coordinates; it does not implement, merge, or deploy.** Proven on a 9-workstream / 2-repo run: all PRs reached tri-model-approved + CI-green with no human babysitting.

This skill assumes an **agent bus** that can spawn headless CLI coding agents and route messages between them. The examples use `hcom` as that bus and `claude` / `codex` / `agy` (antigravity) as the three models, but the doctrine is bus- and model-agnostic — substitute your own.

## When to use
- A spec/plan decomposes into ≥3 independent workstreams, often across repos.
- You want parallelism + worktree isolation + an adversarial review gate before a human merges.
- You have an agent bus that can spawn coding agents (e.g. `claude`/`codex`/`agy`) headless.

**Not for:** a single small change, work needing no isolation, or anything you'll merge yourself immediately.

## The loop
1. **Ground in a master plan first.** It must carry: file:line anchors, a dependency graph, a wave schedule, locked decisions, and known gotchas. Read it fully before dispatching. No plan → write/extend one first.
2. **One agent per workstream**, each: its own git worktree (off the integration branch), headless + autonomous, handed an **inline brief** = its ticket + the relevant plan section + DoD + a shared `_common.md` rules file (merge policy, DoD gate, gotchas). **Foundation/contract workstreams (shared wire formats, schemas) land/freeze FIRST** so dependents build against a fixed contract.
3. **Wave dispatch by dependency.** Launch independent streams together; gate later waves on their deps clearing. Dependent workstreams **stack** on the dependency's branch — but prefer to **merge-as-you-go and pin dependents to a merged commit** where the workflow allows it; stack on an unmerged branch only when you genuinely can't merge yet (never "pin to a branch now, redo the pin later").
4. **Phase R review gate per PR** (see below).
5. **Live `STATUS.md` tracker:** per-workstream board, per-PR review ledger (tri-model verdicts + CI), DECISIONS-NEEDED queue, resolved-decisions log, integration-watch, event log. Update as state changes — it's the source of truth and the human's handoff.
6. **Don't merge / deploy.** Leave every PR "ready to land"; surface decisions to the human.

## Phase R — multi-model review gate (per PR)
> Host-specific spawn recipe (verified flags, the approval-hook trap, the agy warm-up fix, the direct-CLI fallback): **[phase-r-runbook.md](phase-r-runbook.md)**.
- Spawn **3 fresh agents — one `claude`, one `codex`, one `agy` (antigravity)** (fresh = no implementer anchoring; this roster uses `agy`, not `gemini`). Each reviews for **correctness / security / spec+DoD compliance**, not style. **Launch them in parallel + backgrounded via `phase-r-spawn.sh <orch> <repo> <pr> <tag>`** (returns in <1s, three spawns fire concurrently — don't serialize or block on readiness); see [phase-r-runbook.md](phase-r-runbook.md) §2.
- **Get all three verdicts before you judge the round — don't proceed on 2/3.** A missing third verdict is usually a silent-dropped send (see **Bus identity is soft state**) or an idle agent that finished but skipped its final send, not a real abstention. Nudge/reclaim and collect the third; a 2/3 "consensus" has thrown away the one model that might dissent.
- **Don't waive the gate because a PR "looks mechanical."** Mechanical-looking diffs are exactly where an un-run gate hides a real regression. Run the gate on every PR; if the human wants to skip it, that's the human's call, not the orchestrator's.
- **One writer per fix round** (never let multiple agents push the same branch). The finder usually owns its fix; the implementer can apply surgical fixes to its own code.
- **Reviewers must be write-isolated.** Give each reviewer its OWN worktree to build in, but ensure it has NO writable path to the branch under review, and **never name the integrator/writer worktree in a brief**. A headless reviewer under full autonomy (`--dangerously-*`; agy/codex are NOT read-only sandboxed) that decides to "help" will write wherever it can reach — if the only branch-attached worktree on disk is yours, it writes/commits/pushes there and you get a multi-writer collision. That is competent agent behavior your topology failed to contain, **not** a "flaky model." Detached-HEAD review worktrees are not enough (a determined agent finds the attached one); the fix is to leave it nowhere shared to land.
- **+1 truly-fresh reviewer** on the highest-stakes PRs (consensus/security/state-machine), since the loop's reviewers also drove fixes. **Author the hardest work with your strongest coding model, and make that +1 reviewer a *different* model than the author** — a same-model reviewer shares the author's blind spots.
- **Collect verdicts by reading the `REVIEW-<tag>-<model>.md` files, not just the bus.** Delivery to `@<orch>` fails *silently* if your bus identity drifted (send "succeeds," `delivered_to: []`, no error) — so "no message arrived" ≠ "no verdict." The files are the record; the bus send is a ping. See **Bus identity is soft state** below.
- **Terminate on:** all reviewers `ready` (no blocking issue) **AND** CI **observed green** (not "looks fixed") **AND** every gh review thread resolved (verify via `gh`, not eyeballed). Cap ~3 rounds, then escalate — but the cap is a **spin detector, not a budget** (see Phase G).

## Phase G — "grind to green" (Phase R, looped, until landable)
**The named command.** "Run **Phase R** on PR #N" = run ONE advisory gate round, report verdicts, **do not fix**. "Run **Phase G** on PR #N" = **drive that PR to landable**: loop Phase R, apply fixes between rounds, repeat until it converges or escalate. Same gate, but G owns the outcome (R owns the assessment). When the human just names "Phase G #N" with no other instruction, that IS the instruction: converge it.
- **The loop (round k):** (1) run the Phase-R gate (3 fresh reviewers; +1 truly-fresh on high-stakes); (2) **adjudicate contested findings against the source, never majority-vote** → the round's BLOCK/SHOULD-FIX list; (3) if anything must change, **ONE writer** applies it and pushes to the PR branch (finder usually owns its fix; reviewers stay read-only + isolated); (4) wait for CI to re-run; (5) re-gate round k+1 — as in Phase R, the finder usually owns its fix and reviewers may persist across rounds, so **add a +1 truly-fresh reviewer on high-stakes PRs to offset the anchoring of any reviewer who drove a fix** (re-spawning all reviewers fresh each round is the higher-rigor option, not the default).
- **Guard your identity every round, not just at round 0.** A G-loop that dispatches/resumes a writer each round is the *most* drift-prone thing in this skill (see **Bus identity is soft state**): each round re-check `hcom list self`==`<orch>` and collect verdicts from the `REVIEW-<tag>-<model>.md` files, not the bus. **This is a Phase-G-specific trap:** a silently-dropped verdict is indistinguishable from "reviewers didn't approve," so drift makes G **burn the round cap and false-escalate a PR that actually passed.** Before escalating "stuck / no verdicts," rule out drift (check self, read the files, `hcom start --as <orch>` to reclaim, re-collect) — *then* judge convergence.
- **The ~3-round cap is a spin detector, not a budget.** It exists to catch a loop that isn't converging — a fix that keeps regressing, a genuine 3-way standoff, real spec ambiguity — not to force a stop at exactly three. If each round is closing real findings and the trajectory is toward green, keep going; if two rounds produced no forward motion, stop and escalate. Escalate on *deadlock*, not on a counter.
- **Terminate Phase G on the Phase-R terminate condition** (all reviewers `ready` **AND** CI observed green **AND** all gh threads resolved). **Round 0 may be a rebase** if the PR is `CONFLICTING`. Escalate early on genuine spec ambiguity (→ DECISIONS-NEEDED), persistent 3-way disagreement, or a fix that keeps regressing.
- **Phase G still does NOT merge/deploy** — it ends at "landable," the human lands it. Track the round number in the `STATUS.md` ledger's `Round` column.
- Full per-round operational recipe (writer selection, CI-wait, fresh-reviewer re-spawn, the single-PR writer substitute): **[phase-r-runbook.md](phase-r-runbook.md) §8**.

## Bus identity is soft state — a verdict must never depend on it
`@<orch>` is **not durable**. It's an `instances` row bound to your session; under a long, subagent-heavy run (Agent-tool spawns, resumes of bus-aware subagents) your session's "self" can drift onto a subagent's agent-id, your friendly name then goes idle and `stale_cleanup` deletes it. After that, **`hcom send @<orch>` silently no-ops** — the send "succeeds," logs `delivered_to: []`, raises no error; reviewers look finished and you receive nothing. This is a topology failure, not a flaky model. Three defenses — **use all three**:
- **File-first verdicts (durable channel).** The reviewer's `REVIEW-<tag>-<model>.md` in its worktree is the verdict of record; the bus send is only a "go look" ping. **Poll the files; never read "no message" as "no verdict."** Immune to every identity failure, and makes recovery lossless.
- **Self-check each round.** `hcom list self` must print `<orch>`; a hex/UUID or "(not participating)" means you drifted — reclaim before trusting delivery.
- **Pin + reclaim.** Pass `--name <orch>` on your OWN `hcom` calls too (the bus rule is "--name on all commands"), and recover drift/cleanup with `hcom start --as <orch>`, then re-verify and re-poll.

Mechanism, detection commands, and DB-grounded evidence: [phase-r-runbook.md](phase-r-runbook.md) §9. `phase-r-spawn.sh` warns when `self`≠`<orch>` before it launches a gate.

## Single-PR review variant (you are also the author)
When the job is review-and-fix ONE existing PR (not a fan-out), the same rules bind but the trap inverts — **you** are the writer, so "the orchestrator doesn't implement" needs a concrete substitute. Pick ONE:
- **(a) Delegate the fix** to a single writer agent in its own worktree; you stay a pure orchestrator (preferred when there's real work).
- **(b) You write, but never concurrently with live review agents on that branch.** Apply the fix, push, THEN spawn fresh reviewers against the pushed commit. Hand-editing the branch worktree while autonomous agents run causes literal edit-vs-write races (your `Edit` and their write interleave in the same file).

Either way: exactly one writer, reviewers strictly read-only and isolated, and the writer worktree path stays out of every brief.

## Hard-won lessons (the part that matters most)
- **Verify contested findings against the source — never majority-vote.** Twice the review majority was wrong: once 2 reviewers wanted a "fix" that would have *broken a working PR* (wrong assumption about an encoder); once 1 reviewer caught a real security bug the other two missed (a validation check the change had bypassed, allowing a forged input through). Neither model is reliably right on consensus/security-boundary calls. When reviewers disagree on a factual/technical point, **the orchestrator reads the actual code/spec and decides** — that step changed the outcome both times.
- **Prescriptions and negative claims need the same evidence as findings — they rarely get it.** On one PR every *finding* was sound and independently confirmed; both errors were the review's only unanchored claims — an unreachability call made from a diff-local search, and a remedy prescribed without ever leaving the PR's repo. Findings get anchored to `file:line` because there's something to point at; "do X instead" and "X doesn't exist" have nothing to point at, so they ship unverified next to rigorous work and inherit its credibility. **Make reviewers anchor a fix to the code that makes it work and state the scope searched before claiming absence** — then adjudicate remedies against the source the way you already adjudicate findings.
- **Close the class, not the instance.** When a reviewer finds a bug, ask what *class* it belongs to and sweep the whole class in one round — the same missing check at another call site, the same encoder assumption elsewhere. Partially-closed classes are the main reason review rounds don't converge: round k fixes one instance, round k+1 surfaces its twin, and the loop burns rounds chasing siblings it could have killed together.
- **Review what the diff makes *reachable*, not just the lines it changed.** A small diff can enable a large new consequence (a capability granted, a path newly hit, a state now writable). Reviewers scoped to the changed lines under-call these. Point them at what the change *enables*, and **poll the gate's own output (the REVIEW files + CI) before declaring converged** — don't call it done off a passive "no one objected."
- **Single-repo reviewers under-call cross-repo consequences.** A reviewer scoped to the PR's repo will miss what the change does to a *downstream* consumer in another repo (a dispatcher that now takes a different branch, a caller that now gets a new shape). On capability/contract/wire-format PRs, explicitly task a reviewer with tracing the consequence across the repo boundary.
- **State the threat model before gating, don't let reviewers invent one.** If you don't hand reviewers the trust boundary and what's in/out of scope, they'll define scope by hunting adversarial cases — and either rat-hole on out-of-scope attacks or miss the in-scope boundary you actually care about. Put the threat model in the review brief.
- **Review-comment style.** Root every finding in the spec/plan and in "what works vs. what doesn't," be collaborative, and credit what the PR got right. No model/process meta ("as an AI", "in this round", "the other reviewer said") — the PR author sees a clean technical review, not orchestration plumbing.
- **Nudge idle agents; don't wait passively.** Headless agents often finish their analysis but skip the final `hcom send`, going idle without a verdict. When you're down to the last pending signal, **nudge** — don't stall. Check real status with `hcom list -v` (the short/`--format` list can be stale).
- **`--dangerously-skip-permissions` does NOT bypass PreToolUse hooks.** If your host runs a `PreToolUse` approval hook, headless `claude` agents hang on it even with that flag; `codex`/`agy` are immune (they don't run the host's hooks). Fix = spawn claude with `--dir` under a cwd that the hook auto-approves. Full mechanism + fix in [phase-r-runbook.md](phase-r-runbook.md) §4.
- **agy BOOTS fast (<5s); the only latency is an *un-prompted* first hcom send.** agy's startup is quick — the ~30s blamed on "warm-up" is a headless, un-prompted `agy` re-deriving the bus CLI (`hcom --help`→`status`→`list`→`send --help`) before its first send, so a short `hcom listen` expires and it *looks* dead. That's a bus-integration detour, NOT boot time. Fix = a forceful front-loaded prompt that names the exact command, asserts it's correct, and forbids the discovery (46s→~10s). See [phase-r-runbook.md](phase-r-runbook.md) §3.
- **Resolve spec ambiguity from the FINAL spec, not a guess.** Park *genuine* forks (real spec contradictions, design tradeoffs, persistent 3-way disagreement) in DECISIONS-NEEDED for the human; keep other workstreams moving.
- **Determinism discipline for consensus/state code:** committed-bytes-only (never live/pruned caches), canonical ordering (no HashMap-iteration order leaking into committed bytes), **fail-closed** (divergence → block-reject, never a silent fork), node-local state never injected into committed state. Make reviewers prove these adversarially.
- **Stacked-PR mechanics:** branch a dependent off the dependency's branch; reviewers review the **increment** (`git diff <base>..HEAD`), not the whole PR; **squash-merge** collapses stack/orphan history cleanly; `DIRTY`/`CONFLICTING`/`UNKNOWN` merge-state on stacked PRs is **expected** (base predates the integration branch), not a CI failure. When a branch has orphaned/unrelated history, apply a tree-diff patch (`git apply --3way`) instead of `git merge`. Prefer merging deps and re-pinning dependents to the merged commit over keeping a deep stack alive.
- **CI is "observed green," not "looks fixed."** Large test shards are slow + capacity-queued; poll to completion. And **don't rebase+force-push a green PR just to refresh stale checks** — that can hide a bad merge; verify the merged tree locally instead.
- **Watch for reviewer rabbit-holes / scope creep** (e.g. deep-reviewing the already-approved base crate). Nudge back to the increment + report.
- **Some seams are intentional integration steps.** Live cross-crate wiring that spans several stacked PRs can't be owned by any one of them — deliver each piece behind a clean seam, test in isolation, and document the wiring as the integration-gate step.
- **Try the tool before diagnosing its plumbing.** When a spawn or send seems broken, run the actual command once before theorizing about bindings/paths/config. Half the "the bus is broken" moments are a wrong cwd or a missing flag that one real invocation reveals.

## Quick reference
- **Launch:** `hcom 1 <claude|codex|agy> --tag <ws> --dir <worktree> --headless --hcom-prompt "<short: read your brief at PATH; execute; PR to <branch>; report to @<orch>; do not merge>" <autonomy-flag> --go --name <orch>`
- **Autonomy flags:** claude `--dangerously-skip-permissions` · codex `--dangerously-bypass-approvals-and-sandbox` (NOT `--sandbox read-only` — dies headless) · agy/antigravity `--dangerously-skip-permissions` (NOT `--yolo` — that's gemini's old flag; agy exits 2). Confirm with `hcom <tool> --help`; `--go` actually fires (without it you get a preview). Full recipe: [phase-r-runbook.md](phase-r-runbook.md).
- **Briefs in files; launch with a short prompt pointing to the file** (avoids shell-escaping multi-KB prompts).
- **MANDATE `hcom send ... --file` for any message with code/`§`/backticks/`$()` — don't merely suggest it.** This started as a `gemini`-cli quirk (its shell tool BLOCKS command substitution, so an inline `hcom send -- "...backticks..."` is refused — `command substitution detected` — and the verdict never reaches the bus, making the agent look "idle"/silent when it actually finished). Re-verify whether `agy` has the same guard, but `--file` is the safe default for ALL models. Put it in every brief: *write your report to a file, then `hcom send @<orch> --file <path>`*.
- **End your turn to receive bus messages; don't sit in a blocking wait.** On a bus that self-delivers messages into your context (hcom injects `<hcom>` tags at turn-end), just end the turn — use `hcom listen`/sleep only when waiting on something the bus won't push to you. Poll actively (`hcom events sub`) when watching agent progress.
- **One launch per command** (a garbled multi-launch loop spawned a duplicate agent → `hcom kill` both + `git reset --hard`/`clean` the worktree + relaunch one).
- **Guard your bus name:** `hcom list self` must print `<orch>` (check each round); it drifts under long subagent-heavy runs and delivery to a lost name silently no-ops. Pin with `--name <orch>` on your own calls; reclaim with `hcom start --as <orch>`; always also read verdicts from the `REVIEW-<tag>-<model>.md` files. See **Bus identity is soft state**.
- **Post-run hygiene:** if you joined the bus (`hcom start`), run `hcom stop <yourname>` when the run ends — otherwise the Stop hook keeps running `hcom poll` and blocks/injects on every turn-end. `hcom kill tag:<t>` dead reviewer agents and `git worktree remove` their worktrees so the next run isn't confused by stale state.
- Templates (`_common.md`, per-workstream brief, Phase-R review brief, `STATUS.md` skeleton): see [orchestration-templates.md](orchestration-templates.md).
- Host-specific spawn/operation runbook (verified flags, the approval-hook trap, the agy warm-up fix, the direct-CLI fallback, the one-writer-per-branch lesson): see [phase-r-runbook.md](phase-r-runbook.md).

## Common mistakes
- Dispatching before grounding in the plan (or with no plan).
- Trusting the review *majority* on a contested technical call instead of reading the source.
- Proceeding on 2/3 verdicts instead of collecting the third (it's usually dropped/idle, not abstaining).
- Waiving the gate because a PR "looks mechanical."
- Fixing one instance of a bug and moving on while its class stays open (→ non-converging rounds).
- Waiting on a silent/idle agent instead of nudging it.
- Treating stacked-PR `CONFLICTING` state as a CI failure.
- Building dependents before the shared-contract workstream freezes.
- **Implementing the fix yourself in a shared/branch-attached worktree while review agents are live** (single-PR variant) — causes edit-vs-write races and multi-writer commits. One writer; reviewers isolated.
- **Blaming "flaky model" for a collision your topology caused** (a reviewer that writes/commits/pushes was reachable; isolate it instead). A dropped verdict is usually the `--file` send-protocol issue OR your own bus identity having drifted (delivery silently no-ops), not the model.
- **Trusting bus delivery to `@<orch>` as your only verdict channel** — it silently no-ops if your identity drifted/was stale-cleaned. Read the `REVIEW-<tag>-<model>.md` files; self-check `hcom list self`.
- Treating the ~3-round cap as a hard budget instead of a spin detector (stop on deadlock, not on a counter).
- Merging or deploying (the orchestrator never does — the human lands it).
